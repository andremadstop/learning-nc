- `CertificateMapper::findByUserAndCourse(userId, courseId): ?Certificate` — UNFILTERED, returns the NEWEST cert by issued_at regardless of revoked/expires_at/active_idem_key. This is Branch A's lookup.

- `learning_assignments.active_period_key` (Version009400, UNIQUE, value "{courseId}:{subjectType}:{subjectId}", NULLABLE) — the assignment-level "one active period" slot. Assignments have NO active_idem_key column (the research/old-stub PHPDoc is WRONG — correct it).

CORRECTED UNION GUARD (Codex must confirm it closes every property):
> A pass may emit + issue iff EITHER
>   (A) hasEverIssuedCertificate(user,course) === false   [findByUserAndCourse() === null, UNFILTERED — self-learner first cert / ASSIGN-04; also stops infinite self-learner re-issue since a revoked/expired row still counts], OR
>   (B) an OPEN PER-USER period exists: a learning_assignments row with subject_type='user', subject_id=user, course_id=course, active_period_key IS NOT NULL, AND status IN ('assigned','in_progress','overdue')   [allow-list; terminal states cancelled/withdrawn/closed/expired/passed/typos are NON-issuing].
> Within an open period, after issue transition status → 'passed' (markPassed) so a 2nd /pass-status (status='passed') does NOT re-emit/re-issue.

ATOMICITY (the SELECT→INSERT race in emitPassEventIfFirst is now load-bearing):
- Pass the exact period token (active_period_key / assignment id) into issuance.
- The cert insert's `active_idem_key` UNIQUE index IS the CAS win. emit COURSE_PASSED and markPassed(status=passed) happen ONLY on the winning path (after the successful cert insert), so two concurrent /pass-status produce EXACTLY ONE cert AND EXACTLY ONE course.passed event. Prefer a single transaction wrapping {cert insert → COURSE_PASSED → markPassed}; if a transaction across services is impractical, gate the event+markPassed strictly on the cert-insert CAS win (catch REASON_UNIQUE_CONSTRAINT_VIOLATION → loser emits nothing).

BEHAVIOUR MATRIX (must hold):
| Situation | findByUserAndCourse | open per-user period (allow-listed)? | (re)issue? |
| self-learner first pass | null | n/a | YES (A) |
| self-learner, has any cert (valid/expired/revoked), no assignment | non-null | none | NO |
| same period, 2nd GET | non-null | status=passed | NO |
| instructor punitive revoke, no open period | non-null (revoked row) | none | NO (bug avoided) |
| period-close → new pass | non-null (old expired) | fresh row status=assigned | YES |
| two concurrent passes, open period | — | yes | exactly ONE cert + ONE event |

DST date-math (replaces IssuanceService line ~103 `$issuedAt + $validityDays*86400`):
```php
$months = $assignmentOverrideMonths ?? $course->getCertValidityMonths() ?? 12;
$expiresAt = $months > 0
  ? (new \DateTimeImmutable('@'.$issuedAt))->setTimezone(new \DateTimeZone($serverTz))->modify('+'.$months.' months')->getTimestamp()
  : null;
```

closePeriod WRITE-SET (corrected — 4 writes, none of them `revoked`):
1. On the CURRENT cert (findByUserAndCourse): set `expires_at = now - 1` (past) — REQUIRED so verify reads 'expired'; leaving keys nulled alone does NOT expire a cert whose expires_at is NULL/future.
2. On the CURRENT cert: set `active_idem_key = NULL` (learning_certificates) — frees the cert UNIQUE slot so the next-period cert insert does not collide.
3. On the assignment: set `active_period_key = NULL` — frees the assignment UNIQUE slot.
4. INSERT a fresh assignment row (subject_type='user', status='assigned', active_period_key = same "{courseId}:user:{userId}" string). A 2nd close re-INSERT hits the assignment UNIQUE → caught → exactly one new row (SC3 idempotency).
DO NOT set revoked/revoked_at (verify keys on getRevoked() bool → stays 'expired' per SC2; revoked=true would read 'withdrawn'). Audit via AuditService::logComplianceEvent (facts only: course_id, verification_id, timestamps — NO PII in context_json).

A group-originated obligation MUST therefore materialize PER-USER period rows (expandGroup → one subject_type='user' assignment row per member), so one member's pass transitions only that member's row and every member can recert independently. The shared subject_type='group' row (if any) is a template, NOT the per-user period state.
